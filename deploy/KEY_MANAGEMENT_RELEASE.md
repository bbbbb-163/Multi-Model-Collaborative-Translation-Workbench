# 分发密钥恢复与逐次用量：首次发布说明

本说明对应“管理员查看完整分发密钥、按密钥和模型查看请求及用量”的增量功能。当前仅在本地功能分支实现与验证，未推送 main，未操作生产服务器。现有 main 自动部署继续保持原有状态。

## 使用行为

- 管理员在“分发密钥 → 选择密钥”中可查看、隐藏、复制完整密钥。普通用户、匿名请求、后台 bootstrap 列表及工作台接口均不能获取完整密钥或加密副本。
- 新分发密钥使用现有 vault.key 加密保存；登录仍使用原 access_keys.hash 校验，既有密钥 ID、授权、有效期和归属保持。
- 旧密钥只有摘要，不能还原。已知旧密钥下一次成功登录会补存加密副本；错误登录不会补存或修改凭据。已经遗失时，管理员可以明确确认“重新生成”：旧密钥及其用户会话失效，运行停止，原 ID、已保存授权、任务、文件、历史及用量保留。不会自动重置任何已有密钥。
- 请求与用量页支持开始/结束日期、模型、状态筛选、分页、按模型汇总及逐次记录。记录请求时间、状态、耗时、上游返回的输入/输出/总 Token 和媒体产出文件数。
- 工具后续轮次及不支持工具时的回退分别按真实模型请求计数；媒体状态轮询不额外计为生成请求。只记录用户使用平台分配的 Mstar 模型，排除管理员连通测试及用户个人连接。
- Token 只采用上游实际报告的数值；未提供时保留 NULL 并显示“—”，不是零，不估算费用。图片/音频/视频按已返回文件数量统计，不声称等同上游计费量。请求详情不保存提示词、输出正文、凭据或原始上游错误。
- 统计从功能首次初始化后开始；既有任务未保存完整历史请求与上游用量，无法准确补录。删除任务不会删除请求账本。进程重启时，遗留运行中的请求标为“服务中断”。

## 数据变化

采用增量、幂等初始化，不删除或重建现有八张表，不改变原列或原记录：

1. 新增 access_key_secrets：id 引用原 access_keys.id，secret 保存现有 vault 加密格式的密文。撤销并删除原密钥时级联删除该密文，不删除历史请求账本。
2. 新增 model_requests 与三个按密钥、时间、模型及状态查询的索引，保存请求元数据和实际用量。
3. 在 security 中 INSERT OR IGNORE 一条 request-usage-started-at 元数据。admin-password 记录、现有 vault.key 和 provider 密文不变。
4. data_guard 增加对上述两张表的可选清单检查，仍兼容旧备份。新增密文表行不可意外改变，请求账本不能丢记录；现有 schema/vault 兼容性保护不放宽。

## 首次上线必须走受控迁移

这不是可直接由普通 main Push 放行的发布：server/store.ts、server/auth.ts、两份新增 SQL 模块和 deploy/auto/data_guard.py 会触发现有完整性保护；生产 schema 也将由八张表变为十张表。不能只更新文件摘要而忽略 schema 与回滚兼容性，否则现有 worker 会按设计阻断或保留现场。

建议在获得首次迁移授权后，沿用现有部署机制完成：

1. 暂停部署定时器，确认没有用户任务、部署或历史事件误入队，重新检查资源；保留现有生产版本及旧镜像。
2. 取得最新一致性数据/配置备份及站外副本。现行备份会短暂停服，需要在该阶段明确说明并获准。
3. 从已审查、普通推送的提交构建候选镜像；先通过既有 node/合成数据隔离启动关卡，再使用私有恢复副本验证真实旧数据的增量升级。隔离环境不访问生产数据目录，不发布端口或调用真实模型。
4. 用升级后的数据副本实际验证当前旧版生产镜像仍能启动并保留旧记录、密钥和附件，建立经审查的新 schema 兼容回滚基线。未验证之前，不把旧镜像的 schema 标记改成新值，也不声称自动回滚已具备条件。
5. 在明确授权下应用增量迁移，并对八张旧表、管理员、hash、provider 密文、vault 和附件逐项比对。仅将已验证兼容的旧生产版本记录为新 schema 回滚基线；保持当前线上旧 SHA 的真实值，不伪造为新版本。
6. 备份控制状态及原 guards，审查并同步必要的保护条目，安装对应的数据校验代码，保留全部其他状态和安全机制。摘要同步不能代替数据迁移与兼容验证。
7. 只放行本次获准的新事件，由已有 worker 完成构建、隔离启动、备份、切换、健康和数据验收；失败时保留旧版，schema/vault 不兼容则停止，禁止自动覆盖数据库。
8. 完成管理员密钥查看和一次明确授权的真实用量验收后，再恢复长期定时器。保留原凭据和回滚镜像，不发送额外测试部署。

本地迁移回归使用真实旧八表格式的隔离 fixture，验证新代码初始化两次后旧记录、归属、会话、附件、vault 和 provider 解密保持，旧格式查询仍可读。该结果不替代生产 Linux 镜像配合真实恢复副本的首次迁移验收。

## 检查入口

部署前本地验证命令：

```text
npm test
npm run build
python -B -m unittest discover -s tests -p test_auto_deploy.py
npx tsx tests/admin-key-management-browser.ts
npx tsx tests/mstar-browser.ts
node tests/production-smoke.mjs
```

新增管理员接口（均受原有 requireAdmin 和同源限制保护）：

- POST /api/admin/keys/:id/secret：按需解密，Cache-Control: no-store。
- POST /api/admin/keys/:id/rotate：明确的凭据重新生成，保留 ID/归属/授权并终止旧用户会话。
- GET /api/admin/keys/:id/usage：按密钥固定查询范围，参数化过滤，固定每页 25 条。

上线后仍需核对实际容器 revision 与 Gitee main 完整 SHA、healthy、HTTPS、八张旧表与新增账本清单，以及管理员/普通用户权限隔离。源码包含受保护变更，不应在首次迁移审核之前直接推送 main 试探部署。
